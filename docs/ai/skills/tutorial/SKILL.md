# 一、平台优势

## 驱动覆盖面广，开箱即用

内置 Modbus、DTU、MQTT、OPC UA、西门子、欧姆龙、三菱、罗克韦尔、汇川、松下、Fanuc CNC、DLT645、IEC104、IEC61850 等主流工业协议驱动，覆盖工业自动化和电力两大领域。客户不需要再花时间找第三方驱动或自己开发。

## 脚本引擎嵌入数据管道，减少定制开发

数据过滤（变化检测入库）、数据解析（字节转换/复合计算）、计算属性（二次计算）、联动脚本（自动化逻辑）——四个环节全部支持页面编写 JS 脚本。非标需求无需二次开发，直接在页面写脚本解决。

## 采集粒度灵活：频率标签 + 采集器分层

不是整个产品一个采集频率，而是每个事件模型打频率标签，采集器按频率范围筛选。同一个设备下，温度可 1s 采集、压力 5s 采集、状态 30s 采集，精细控制采集负载。

## 驱动与网络组件解耦 + Modbus 批量采集

驱动只负责数据翻译，网络组件负责通信链路，一个驱动可复用给不同网络拓扑。Modbus 自动按功能码分组、地址排序、包长拆分，省去手动配点位的工作量。

## 场景联动 + 联动脚本双机制

简单的 if-then 用场景联动，复杂的多条件/累计/连续判断用联动脚本，覆盖从简单到复杂的自动化需求。

## 物模型：专为按点位采集的工业协议设计

多数 IoT 平台的物模型只处理 JSON 键值对，无法表达 Modbus 寄存器、PLC 数据块这类按地址采集的数据。平台通过**属性 + 事件模型 + 功能模型 + 容器类型 + 字典** 的组合，将底层协议的数据点位与业务操作完整解耦：

- **事件模型**选择驱动指令，**上行配置**通过 `@` 绑定到模型属性，完成"采集哪个地址 → 映射到哪个属性"
- **属性字典**为枚举属性预定义值的含义（如开=true、关=false），功能模型下行配置绑定该属性后，自动将控制接口拆分为多个操作项
- **容器类型**（json/group/bit）将复杂返回展开为多个子字段
- 驱动层只关心"用什么指令、读哪个地址"，业务层只关心"这个属性叫什么、值是什么"，两层通过物模型衔接

> 与通用 IoT 平台的完整差异对比见：[物模型创新点](./references/innovation-points.md)

# 二、设计理念：模型驱动，而非代码驱动

## 传统做法：每步都要写代码

一台设备从接进来、到能在屏幕上看到数据，通常要走这几步：

```
设备数据 → 写代码解析协议 → 写代码转换数据 → 写控制逻辑 → 写界面展示
```

每一步都离不开程序员。换一个设备、加一个采集点、改一个控制逻辑，又得找程序员改代码。一个项目做完，下一个项目还得从头来一遍。

## 平台的做法：配配置就行

平台把"写代码"变成了"填表单"：

```
设备数据 → 驱动（选一个）→ 物模型（配一下）→ 采集控制（设个频率）→ 界面自动出来
```

整个过程在页面上点一点、选一选就完成了，不需要写一行代码。

打个比方：传统做法就像**自己造手机**——从焊电路板开始，每个零件都要自己弄。平台的做法就像**买一部智能手机**——系统已经装好了，你要做的只是装个 App、设置一下就能用。

## 核心：物模型就是"翻译官"

平台分三层，各干各的活：

```
┌─────────────────────────────────────┐
│  界面层 — 你看到的样子，自动生成      │
├─────────────────────────────────────┤
│  物模型层 — 你说的话，设备听得懂      │
│  属性（有什么数据）+ 字典（值啥意思）  │
│  功能模型（能做什么操作）              │
│  事件模型（采什么、多久采一次）         │
├─────────────────────────────────────┤
│  驱动层 — 跟设备打交道               │
│  Modbus / PLC / OPC UA ...          │
└─────────────────────────────────────┘
```

- **驱动层**：负责和设备"说话"。它知道怎么用 Modbus 读数据、怎么用 PLC 写指令，但它不关心这些数据是什么意思。
- **物模型层**：负责"翻译"。它告诉驱动：去读哪个地址、读回来的数据叫什么名字（温度还是压力）、值代表什么意思（1 是开、0 是关）。反过来，操作员在界面上点"打开阀门"，物模型把它翻译成驱动能懂的指令，发给设备执行。
- **界面层**：物模型配好之后，界面自动就生成了——设备列表显示什么、详情页有哪些数据、控制面板有哪些按钮，全由物模型决定。

再打个比方：驱动就像**快递员**——他负责把包裹从 A 送到 B，但他不知道里面装的是什么。物模型就是包裹上的**快递单**——写着"这是什么、送到哪、怎么处理"。界面就是**收件人看到的物流信息**——自动显示包裹到哪了、预计啥时候到。

## 这样做的几个好处

**第一个项目**：配驱动、建产品、定义物模型、创建设备、配置采集器——全部在页面上点一点就完成，零代码。

**第二个项目**：同类型的设备直接用之前配好的模板，新设备只需要建个新产品、改改物模型就行。驱动不用重配，界面自动就有了。

**日常运维**：想加一个采集点 → 物模型加个属性；想改控制逻辑 → 物模型改个绑定。不需要提需求、等排期、改代码、重新发布。

## 配一次，手机和电脑都能用

物模型配置完成后，管理端（PC 后台）和移动端（手机 App）的界面会自动适配——哪些数据要展示、控制面板有哪些按钮，都由物模型决定。不用给 PC 和手机分别开发两套界面。
