# 物模型创新点：与通用 IoT 平台的区别

市面上多数 IoT 平台（如阿里云 IoT、AWS IoT、腾讯云 IoT）的物模型围绕 JSON 键值对设计，面向互联网消费类设备。本平台面向工业场景，核心差异如下：

## 1. 设计起点不同：点位采集 vs JSON 键值对

**通用平台：** 设备上报 JSON → 属性值以 JSON 字段映射。属性定义就是"给一个字段起个名、定个类型"。遇到 Modbus 寄存器、PLC 数据块这种按地址读的数据，需要写代码转换。

**本平台：** 属性只声明"有什么数据"，通过**事件模型**选择驱动指令、用 `@` 绑定到属性，一个配置完成"从哪个地址读到哪个属性"。驱动层只关心地址和指令，业务层只关心属性名和值，中间由事件模型的`上行配置`衔接。

## 2. 容器类型：处理复杂的工业数据结构

**通用平台：** 属性只有基本类型（int/float/string/bool），一个属性对应一个值。遇到"一个寄存器不同比特位代表不同含义"或"一条返回包含多个字段"时，要么拆成多个属性，要么写脚本解析。

**本平台：** 三种容器类型专门处理复杂数据：
- **bit** — 一个数值的不同比特位自动按位拆成多个子字段，无需脚本
- **json** — 事件返回 JSON 时按路径展开为多个子字段
- **group** — 把多个相关属性逻辑归组

容器类型的属性本身不显示，显示的是展开后的子字段，对上层透明。

## 3. 属性字典 + 控制自动拆分

**通用平台：** 枚举属性通常需要用户手动填写枚举值。下发控制时，用户输入 true/false 或开关值。

**本平台：** 属性配置字典（名称=开，值=true），功能模型下行配置绑定该属性后，控制接口自动拆分为"控制→开"和"控制→关"两个独立按钮。工厂操作员直接点击按钮操作，不需要理解 true/false。

## 4. 频率标签 + 采集器分层控制

**通用平台：** 通常是"产品级采集频率"或"设备级采集频率"，所有属性一个频率。

**本平台：** 每个事件模型带频率标签（如 1s、5s、30s），采集器按频率范围筛选。同一个设备下温度 1s 采集、压力 5s 采集、状态 30s 采集，精细控制采集负载和存储成本。

## 5. 驱动与网络组件解耦

**通用平台：** 协议解析和通信链路通常绑在一起，换网络方式需要重配驱动。

**本平台：** 驱动只负责协议翻译（Modbus/PLC/OPC UA 等数据格式），网络组件负责通信链路（TCP/串口等）。同一个 Modbus 驱动可同时服务 TCP 链路和串口链路，一个驱动可复用于不同网络拓扑。

## 6. 计算属性与数据解析分离

**通用平台：** 通常只有一层属性值转换，解析和计算混在一起。

**本平台：** 明确分为两层：
- **数据解析（值解析器）** — 发生在采集时，把字节转为可读值（如两个 Modbus 寄存器拼成 float）
- **计算属性** — 发生在采集后，对已解析的数值做二次计算（如脉冲数 × 系数 = 流量）

各管各的，职责清晰。

## 7. 功能模型控制状态

**通用平台：** 所有控制接口在界面上平铺展示，不受限。

**本平台：** 一个产品可能定义多个功能模型接口，但移动端空间有限。标记为"控制状态"的接口被识别为核心操作，在空间受限场景下优先展示，用户可直接操作无需进入二级页面。这是面向移动端现场操作的设计。
