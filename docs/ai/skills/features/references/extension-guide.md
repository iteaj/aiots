# 功能扩展设计规范

## 新增功能的流程

### 第一步：需求分析

回答以下问题：
- **背景：** 为什么需要这个功能？解决什么业务问题？
- **用户：** 谁在用这个功能？（工厂负责人/技术负责人/运维人员/系统集成商）
- **触发：** 什么场景下会用到这个功能？（日常巡检/故障处理/设备接入/数据查看）

### 第二步：影响评估

- 涉及哪些模块？后端/管理端/移动端？
- 需要数据库变更吗？DDL 追加到 `docs/sql/patch.sql`
- 是否需要新表或新字段？现有表结构能否复用？
- 影响范围：这个变更会影响现有功能吗？需要兼容处理吗？

### 第三步：方案设计

- 技术选型参考同类功能现有实现模式
- 后端遵循 @RestController + MyBatis Plus + Entity/DTO/VO 模式
- 数据库设计遵循现有表命名规范
- 前端模式：
  - 管理端：Vue3 + Ant Design Vue + UTable/UDrawer/UForm 模板
  - 移动端：uni-app x + Cool UI 组件

### 第四步：用户确认

整理前三步内容，向用户确认后再开始开发。

### 第五步：上线归档

功能上线后：
1. 更新 `feature-catalog.md`，标注状态为 ✅
2. 如有推广价值，补充"推广角度"列
3. 检查是否需要更新 `design-decisions.md`（新增决策记录）
4. 如点子池中有相关 idea，标注为"已实现"

## 设计原则

### 最小改动原则
- 尽量复用现有表结构，不轻易建新表
- 能用配置解决的不用代码，能用现有字段扩展的不加字段

### 先判断基座
- 新增功能先判断属于哪个基座（CRUD/管理端/移动端/驱动/插件）
- 按对应基座的技能模板和流程开发

### 确认三原则
- 原子化：每次只确认一个事项
- 简洁明确：控制在 5 行以内
- 用户主导：不代替用户做决定

### 后端先于前端
- 先确定接口 URL、参数、响应，再开发前端
- 前端接口 URL、参数、方法与后端保持一致

### 数据库变更规范
- 所有 DDL 追加到 `docs/sql/patch.sql`
- 需标注时间注释
- 考虑现有数据兼容（初始化默认值）
