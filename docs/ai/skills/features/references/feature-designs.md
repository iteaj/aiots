# 功能设计背景

按模块记录每个功能点的设计背景——为什么有这个功能、解决什么问题、怎么用。

---

## 基础架构

### 模型驱动架构：配配置不写代码
**背景：** 传统 IoT 项目每接一台设备都要写协议解析、数据转换、界面展示，开发和维护成本极高。平台把"写代码"变成"填表单"——选驱动、配物模型、设频率，界面自动生成。非标需求用脚本引擎页面解决，不需要改代码重新发布。

### 物模型三层架构
**背景：** 工业设备的数据不是 JSON 键值对，而是寄存器地址、协议帧、比特位。三层架构让各层各司其职：驱动层跟设备通信，物模型层翻译数据，界面层自动生成 UI。改一层不影响另外两层。

### 驱动与网络组件解耦
**背景：** 传统做法把协议解析和通信链路绑在一起，Modbus RTU（串口）和 Modbus TCP（以太网）要用两个驱动。解耦后一个 Modbus 驱动同时服务 RTU 和 TCP，网络组件独立替换。

### 一次配置多端适配
**背景：** 很多平台需要分别为 PC 管理端和手机 App 开发界面，工作量翻倍。物模型配好后，管理端和移动端的界面自动适配同一套物模型定义，数据展示和控制按钮自动生成。

### 零代码运维
**背景：** 传统模式下加一个采集点、改一个控制逻辑，需要提需求、等排期、改代码、重新发布。平台上加属性、改绑定、配告警都在页面完成，不需要经过开发流程。

### SPI 机制支持自定义驱动扩展
**背景：** 平台内置的驱动不可能覆盖所有设备协议。通过 DeviceProtocolSupplier SPI 接口，第三方可以编写自定义驱动并注入平台，平台本身代码不需要修改。

## 协议驱动

### Modbus RTU/TCP 驱动
**背景：** Modbus 是工业领域最通用的通信协议，支持串口（RTU）和以太网（TCP）。几乎所有 PLC、传感器、仪表都支持 Modbus，是设备接入的首选协议。

### 西门子 S7 驱动
**背景：** 西门子是国内市场占有率最高的 PLC 品牌，S7-200/Smart/1200/1500 覆盖从小型到中大型控制系统。平台直接读写 PLC 数据块，不需要通过 OPC 服务器中转。

### 欧姆龙驱动
**背景：** 欧姆龙 PLC 在包装、电子行业广泛使用，HostLink 协议通过串口通信，CIP 协议基于以太网。平台同时支持两种通信方式。

### 三菱 FX5U 驱动
**背景：** 三菱 PLC 在中小型设备中应用广泛，FX5U 是三菱主推的系列。平台通过 MC 协议直接读写三菱 PLC 数据寄存器。

### 罗克韦尔 PLC 驱动
**背景：** 罗克韦尔（AB）PLC 在北美市场和中国高端制造业中有较高占有率，大中型项目中常见。

### 汇川 PLC 驱动
**背景：** 汇川是国内领先的自动化厂商，在电梯、注塑机、纺织机械等领域有大量装机量。

### 松下 PLC 驱动
**背景：** 松下 PLC 在小型设备和 OEM 市场有一定规模，主要用于包装、电子制造等场景。

### OPC UA 驱动
**背景：** OPC UA 是工业 4.0 推荐的通信标准，解决了传统 OPC 依赖 Windows COM/DCOM 的跨平台问题。支持数据加密、证书认证，适合对安全性要求高的跨系统对接场景。

### MQTT 驱动
**背景：** MQTT 是物联网领域最流行的轻量级消息协议，适合带宽有限、网络不稳定的场景。很多新型工业设备和传感器直接支持 MQTT 上报数据。

### DTU 透传驱动
**背景：** 老旧串口设备（如电表、流量计）没有以太网接口，通过 DTU 模块将串口数据转为 TCP 数据发送到平台。平台在接收到 DTU 数据后还原为原始协议帧处理。

### DLT645 电表驱动
**背景：** DLT645 是国家电网标准的多功能电表通信协议，国内电表和能源管理系统普遍使用。平台直接解析 DLT645 协议帧获取电压、电流、功率、电能等数据。

### IEC104 电力远动驱动
**背景：** IEC104 是电力行业标准远动通信协议，用于变电站、光伏电站、风电场的设备监控和数据采集。平台直接对接电力调度系统。

### IEC61850 变电站驱动
**背景：** IEC61850 是智能变电站领域的通信标准，定义了变电站内智能电子设备之间的数据模型和通信服务。用于大型变电站自动化系统。

### Fanuc CNC 数控机床驱动
**背景：** 发那科（Fanuc）是全球最大的数控系统供应商，其机床的数据采集对制造业数字化至关重要。平台通过 Fanuc FOCAS 库读取机床运行状态、主轴负载、加工计数等数据。

### HTTP 驱动
**背景：** 部分设备通过 HTTP 接口上报数据（如 RESTful API、Webhook），HTTP 驱动接收设备 POST 的数据后解析并写入平台。

### 自定义脚本驱动
**背景：** 私有协议、非标设备、小众工业设备，没有现成的驱动支持。用户可以通过编写 JS 脚本实现自定义协议的解析，平台提供数据帧的收发能力。

### 内置驱动预置网络组件和网关产品
**背景：** 用户接入设备时需要先配置网络组件和网关产品，流程繁琐。平台为每个内置驱动预置了对应的网络组件和默认网关产品，用户可以直接创建子产品接设备，省掉前置配置。

## 物模型 - 属性

### 基本数据类型
**背景：** 工业设备上报的数据有整数、浮点数、布尔、字符串、日期等多种类型。平台需要覆盖 byte/short/int/long/float/double/string/boolean/date 共 9 种基本类型，才能适配不同设备的数据格式。

### json 容器类型
**背景：** 事件接口返回的可能是一个复杂的 JSON 对象（如一次上报温度、湿度、压力三个值），需要拆成多个独立属性才能分别查询和分析。json 容器通过配置 JSON 路径（如 `$.data.temp`）将嵌套值展开为子字段。

### bit 容器类型
**背景：** 工业设备中一个寄存器值经常包含多个信号（如第 1 位表示运行状态、第 2 位表示故障状态、第 3-4 位表示运行模式）。bit 容器按比特位拆解，每个信号成为独立属性，便于监控和告警。

### group 容器类型
**背景：** 多个相关的属性（如 A 相电压、B 相电压、C 相电压）逻辑上属于同一组。group 容器将它们归为一组管理，方便在前端统一展示和查询。

### 属性字典配置
**背景：** 设备上报的值通常是编码（0、1、true、false），但操作员需要看到的是含义（开、关、运行、停止）。字典将编码值映射为可读的名称，让数据对操作员友好。

### 属性字典 + 控制自动拆分
**背景：** 一个控制接口如果参数值是枚举类型（如开关控制：on/off），操作员需要知道编码才能操作。字典绑定后，平台自动将"开关控制"拆分为"控制→开"和"控制→关"两个独立按钮，操作员直接点，不需要知道编码。

### 属性序号排序
**背景：** 物模型属性在列表中展示时，默认按创建时间排序，但业务上希望重要的属性排前面（温度排第一、压力排第二）。序号字段让用户自定义展示顺序。

### 操作符
**背景：** 告警条件判断需要灵活的比较方式，不止是大于和小于。平台支持 gt/gte/lt/lte/eq/neq/contain/in/between 共 9 种操作符，覆盖数值比较、字符串匹配、范围判断等场景。

### 阈值设置
**背景：** 告警触发需要一个具体的值作为判断基准。阈值字段配合操作符使用，如"大于 50"表示温度超过 50℃ 时触发。

### 状态指标标签
**背景：** 操作员需要一眼看出数据是正常还是异常，而不是逐个比对数值。状态指标标签（偏高/偏低/过高/过低/正常）在数据旁边显示状态，看颜色和文字就知道数据情况。

### 扩展配置
**背景：** 告警规则未来可能需要更多的参数（如持续时间、抑制规则、升级策略）。扩展配置字段以 JSON 格式存储，支持向前兼容扩展，不需要改表结构。

## 物模型 - 接口

### 功能模型
**背景：** 操作员需要通过平台向设备下发控制指令（打开阀门、启动电机、调节参数）。功能模型定义一个设备可以执行的操作，包括输入参数（控制指令携带的数据）和输出参数（执行结果）。

### 功能模型输入/输出参数
**背景：** 不同控制指令需要不同的参数（开关控制只需要 on/off，参数设置需要键和值）。输入参数定义下发时需要填什么，输出参数定义执行后返回什么。

### 事件模型
**背景：** 平台需要从设备获取数据。事件模型定义采集哪个数据、用什么指令采、采回来的数据映射到哪个属性。包括主动采集（平台定时轮询）和设备主动上报（设备主动推送）两种方式。

### 上行配置 @绑定模型属性
**背景：** 采集回来的数据需要知道映射到哪个模型属性（如读回来的第 1 个值对应温度、第 2 个值对应压力）。在事件模型上行配置中输入 `@` 弹出属性列表选择绑定，完成"采集哪个地址 → 映射到哪个属性"的映射。

### 频率标签
**背景：** 不同数据需要不同的采集频率（温度变化慢可以 10s 采一次，压力变化快需要 1s 采一次）。频率标签打在事件模型上，采集器按频率范围筛选匹配，实现同一设备不同属性不同频率。

### 指令与模型接口的关系
**背景：** 驱动提供的是底层协议操作（如 Modbus 03 读保持寄存器），业务层面需要的是"温度读取"、"压力读取"。模型接口选择驱动指令，告诉驱动"用这个指令来采集或控制"，同一指令可被多个模型接口复用。

### 频率标签 + 采集器分层
**背景：** 每个属性单独配采集器太繁琐，统一频率又浪费资源。频率标签打在事件模型上，采集器配置时选频率范围，自动拉取匹配的事件模型执行，精细控制采集负载。

## 计算属性与控制状态

### 计算属性
**背景：** 设备上报的往往是原始值（脉冲数、电压信号），业务需要的是换算后的值（流量、温度）。计算属性在采集后执行 JS 脚本，通过 `methods.getValue()` 读取已采集值，计算后通过 `methods.updateValue()` 写入另一属性。

### 系数换算
**背景：** 工业场景中最常见的计算——原始值乘以一个系数得到业务值。如脉冲频率 × 标定系数（0.0102）= 瞬时流量。在计算属性脚本中用一行乘法即可完成。

### 统计汇总/累加计算
**背景：** 需要将多个属性的值汇总（如总功率 = 各设备功率之和）或持续累加（如累计产量 = 每次计数 + 上次累计值）。计算属性脚本支持任意 JS 逻辑。

### 计算属性 vs 数据解析的区别
**背景：** 用户容易混淆采集时的数据解析和采集后的计算属性。数据解析是采集时将原始字节转为可读值（二进制转 float），计算属性是对已解析好的业务值做二次计算（值×系数）。职责不同，用在不同的环节。

### 功能模型控制状态
**背景：** 一个产品可能定义多个控制指令，但移动端空间有限，不能全部展示。标记为"控制状态"的指令在移动端优先展示，操作员可直接操作，不用进二级页面。适用于开关、启停等高频操作。

## 告警与指标

### 告警与指标分离设计
**背景：** 传统平台把所有偏离正常的值都当作告警处理，告警列表很快被"噪音"淹没。平台把"需要处理的问题"（告警）和"需要关注的状态"（指标）分开，避免告警疲劳。

### indicator 级别不产生告警记录不推送
**背景：** 大量数据只需要展示状态（偏高/偏低），不需要入库和推送。indicator 级别只在前端显示状态标签，不占告警存储，不打扰操作员。适用于趋势预警、日常巡检等场景。

### WarnGrade 枚举
**背景：** 不同的偏离程度需要不同的处理方式。fatal/urgent/warn/notice/normal/status/indicator 七级枚举覆盖了从严重故障到纯展示的完整分级，每级可以配置不同的通知策略。

### 单属性告警配置
**背景：** 传统的告警配置集中在告警中心，需要关联产品和属性。更自然的做法是把告警配置放在属性上，在物模型编辑时同时配置采集、存储和告警。配置后采集时自动触发判断，不需要额外设置。

### 多属性组合告警
**背景：** 有些告警需要多个条件同时满足才能判断（如温度>50 且 湿度<30），单属性告警无法处理。组合条件放在场景联动中，支持任意条件的 AND/OR 组合。

### 设备状态自动告警
**背景：** 设备上线和离线是最基础的状态变化，每个设备都会发生。如果每个设备都要手动配上下线告警，工作量巨大。平台自动记录设备上下线状态，不需要任何配置。

### 告警模板
**背景：** 不同的告警需要不同的通知内容（故障告警需要包含设备名称和当前值，状态通知只需要简单提示）。告警模板让用户自定义消息格式，按需配置。

### 告警记录查询
**背景：** 告警发生后需要追溯：什么时间、什么设备、什么原因、是否已处理。按设备、时间、级别筛选方便快速定位历史告警，支持管理端和移动端查询。

### 告警类型区分
**背景：** 告警记录来自不同的触发方式（属性阈值触发、场景联动触发、设备状态变化），查看时需要知道来源。通过判断告警配置是否有 operator 和 threshold 字段来区分是属性告警还是其他类型告警。

## 设备管理

### 三种设备类型
**背景：** 工业现场设备组网方式不同：有的直接连平台（直连设备），有的通过网关转发（子设备），网关本身不产生数据。三种类型区分清晰，每种类型的配置和管理方式不同。

### 网关设备模式
**背景：** PLC、DTU 等网关设备负责协议转换和数据转发，本身不产生业务数据。网关下挂的子设备才是数据来源。平台区分网关和子设备，让网关专注于转发，子设备专注于业务数据。

### Modbus 批量采集
**背景：** 传统 Modbus 采集逐点配置，一个温度点、一个压力点各自独立采集，效率低、网络占用高。平台自动按功能码分组、地址排序、包长拆分，将连续的地址合并成批量请求，一次通信采集多个点位。

### 设备分组
**背景：** 设备数量多了以后需要按业务逻辑组织（一车间、二车间、A 产线、B 产线）。树形结构的分组方便运维人员按区域、按产线查找和管理设备。

### 采集器按设备组筛选
**背景：** 一个车间只采集这个车间的设备，不采集其他车间的数据。采集器配置时选择设备组，只对该组下的设备执行采集任务。

### 产品类型分类
**背景：** 不同类别的产品管理方式不同（传感器、执行器、控制器）。产品类型让产品有清晰的分类，方便按类别搜索和筛选。

### 三种产品类型
**背景：** 产品类型对应设备组网方式。直连产品配直连设备，子产品配网关子设备，父产品配网关设备。每种产品的物模型配置要求不同（父产品无物模型）。

### 父产品无物模型
**背景：** 网关只转发数据不产生数据，不需要定义属性、功能模型和事件模型。明确这一点后用户在创建网关产品时不用纠结物模型怎么配。

### 创建设备 7 步标准流程
**背景：** 新用户接第一台设备时不知道从哪里开始。7 步流程（确认驱动→创建产品→配属性→配事件模型→创建设备→配采集器→看数据）给出清晰的指引，跟着做就能完成接入。

### 移动端设备列表
**背景：** 运维人员经常不在电脑前，需要在手机上查看设备状态。移动端设备列表展示设备在线状态、关键数据，支持分组筛选和搜索。

### 移动端设备详情页
**背景：** 查看单个设备的详细信息（实时数据、控制指令、告警记录、指令日志）在手机上完成。5 个 Tab 覆盖设备运维的完整信息。

### 5 个 Tab 详情页
**背景：** 设备详情数据量大，全部展示在一个页面需要大量滚动。用 Tab 分页（详情/实时数据/指令集/告警/指令日志）让信息按类别组织，操作员快速切换到需要看的部分。

## 运行管控

### 运行展板
**背景：** 管理者需要一眼看到全厂设备运行概况——多少设备在线、多少离线、多少有告警。运行展板以卡片形式展示关键统计数据，方便晨会和日常巡检。

### 电子地图
**背景：** 设备分布在不同的物理位置（不同车间、不同厂区），列表无法直观展示空间分布。在地图上标注设备位置和运行状态，管理者可以按地理位置查看设备状况。

### 移动端首页统计卡片
**背景：** 运维人员打开 App 时最关心的是"今天有没有异常"。首页统计卡片展示设备总数/在线/离线/今日告警，不用翻页就能掌握整体情况。

## 数据中心

### 模型数据
**背景：** 需要按物模型维度查看历史数据——选择属性，查看该属性在一段时间内的变化曲线和数值列表。用于分析单个数据点的趋势。

### 产品数据
**背景：** 需要按产品维度查看历史数据——选择产品，查看该产品下所有设备的所有属性数据。用于查看同一类型设备的整体数据情况。

### 通用报表
**背景：** 标准的模型数据/产品数据不能满足所有报表需求。通用报表支持自定义统计维度和聚合方式，用于生成日报、月报等定制化报表。

## 场景联动与事件源

### 场景联动
**背景：** 设备之间需要自动化协作——温度高了自动打开风扇，压力低了自动启动泵。场景联动配置"如果条件满足就执行动作"的规则，实现设备间的自动化控制。

### 多条件组合
**背景：** 单个条件判断容易误报（温度瞬间超限但很快恢复）。多个条件同时判断（温度>50 且 持续时间>30 秒）更可靠，减少误触发。

### 指令联动
**背景：** 自动化规则的最终动作通常是执行设备控制指令。满足条件时平台自动下发指令到指定设备，不需要人介入操作。

### 通知联动
**背景：** 满足条件时需要通知相关人员。通知联动配置短信、邮件、钉钉等通知方式，确保负责人第一时间知道。

### 执行器
**背景：** 有些采集任务需要在固定时间执行（每天 8 点抄表、每 30 分钟巡检），而不是持续采集。执行器通过 cron 表达式定义定时策略，到时间触发采集或联动。

### 采集器
**背景：** 平台需要定时从设备读取数据。采集器配置采集哪类产品、哪些设备组、多高的频率，驱动采集引擎按配置执行。

### 场景联动 vs 单属性告警的分工
**背景：** 用户容易混淆在属性上配置告警和在场景联动中配告警的区别。单属性告警（属性配置）适合简单阈值判断，采集时自动触发；多属性组合（场景联动）适合复杂条件判断，需要先采集到值再判断。

### 联动脚本
**背景：** 场景联动的 if-then 模式只能处理简单逻辑，遇到分级控制、累计计数、闭环调节等复杂场景就不够用了。联动脚本用 JS 写任意逻辑，支持循环、延时、条件分支、函数调用。

## 数据可视化

### 组态
**背景：** 工业现场的管理者需要直观看到设备布局和实时状态，文字表格不够直观。组态通过拖拽设计工业流程图、设备面板，将设备数据以图形化的方式展示在屏幕上。

### 官方预设大屏模板
**背景：** 大多数用户没有设计能力，从零开始做大屏门槛高。平台预设多个行业通用的数据大屏模板，用户可以直接使用或在此基础上修改。

### 大屏素材管理
**背景：** 用户在组态中使用的图片、图标等素材需要统一管理。素材库支持上传、分类、复用，避免每个大屏重复上传相同素材。

## 脚本引擎

### 数据过滤：变化检测入库
**背景：** 很多设备持续上报同样的值（如稳定的压力值），每次都入库会占用大量存储。变化检测（methods.isChange）只在值变化时写入，无变化跳过，减少 80% 以上的无效数据存储。

### 数据过滤：时间间隔过滤
**背景：** 变化太频繁的属性（如振动传感器每秒都在变化）如果每次都入库，数据量仍然很大。时间间隔过滤（methods.isGeIntervalChange）限制了最短入库间隔，降频存储。

### 数据解析：类型转换
**背景：** 设备上报的是原始字节，需要转为业务可读的值。Modbus 寄存器读取的是两个字节，需要拼成 float；PLC 数据字存储方式不同需要转换。平台提供 toHex()、toBytes()、toInt() 等转换工具。

### 数据解析：复合计算
**背景：** 一个设备的真实值可能需要从多个地址组合计算得到（如高位寄存器和低位寄存器合并为一个 32 位值）。复合计算在解析脚本中按业务规则计算最终值。

### 数据解析：分组属性
**背景：** 一条设备数据可能包含多个字段（如一次上报温度、湿度、压力）。通过 methods.addRealtimeData() 在解析脚本中拆分为多条子属性，分别存入不同属性。

### 功能解析
**背景：** 下发控制指令时，有的设备需要把多个参数拼装成固定格式的数据帧才能执行。功能解析在下发时动态组装参数值，确保发出的数据设备能识别。

### 脚本引擎三道关卡
**背景：** 数据处理有多个环节，用户需要知道在哪个环节处理什么问题。过滤（采集时去重）、解析（字节转业务值）、联动（条件判断和控制）三道关卡覆盖了数据处理的全链路，每道关卡处理不同的问题。

### 联动脚本：温度超限分级保护
**背景：** 单次超温就告警容易误报，但连续超温不处理可能损坏设备。脚本实现连续多次采样超温才告警，并且根据超温幅度分级处理——小幅度降速，大幅度停机。

### 联动脚本：产线计数满自动换箱
**背景：** 产线上产品计数满了需要自动切换包装箱，传统做法需要人工盯着。脚本监听传感器计数，达到设定值后自动调用指令驱动推杆换箱，并重置计数器。

### 联动脚本：PID 闭环调节
**背景：** 恒温、恒压控制需要实时调整执行器参数，纯粹的条件判断不够用。脚本实现 PID 控制算法：读取当前值和目标值的偏差，计算输出值，调用执行器调节，形成闭环控制。

### 联动脚本：多条件复合预警
**背景：** 单一传感器误报率高（振动异常可能是路过震动不是设备故障）。脚本联合多个传感器（电流和振动同时异常）才判断为故障，大幅降低误报率。

### 联动脚本：烟叶烘烤工艺模式切换
**背景：** 不同工艺有不同的控制逻辑，固化在代码里不灵活。脚本实现不同烘焙阶段的控制逻辑，操作员在页面切换脚本即可切换整套控制逻辑，支持多种工艺共用同一套硬件。

## 设备维护

### 设备调试
**背景：** 设备接入后需要验证通信是否正常、数据是否正确、指令是否能下发。设备调试工具让操作员选择设备和指令，下发测试指令并查看返回结果，验证通信链路和数据准确性。

### 指令日志
**背景：** 指令下发后需要知道是否成功、耗时多久、返回什么数据。指令日志记录每次下发的指令、参数、结果、操作人、下放时间，用于问题排查和操作审计。

## 移动端 App

### 首页统计
**背景：** 运维人员打开 App 需要快速了解整体设备状况。首页统计卡片展示设备总数、在线数、离线数、今日告警数，不用翻页就知道有没有异常。

### 快捷功能入口
**背景：** App 中常用的功能（设备列表、告警查看、数据浏览）需要快速访问。首页提供图标入口，点击直达对应页面。

### 最新告警列表
**背景：** 运维人员关注最新的告警情况。首页展示最近几条告警记录，点击可查看详情，及时处理。

### 产品概览
**背景：** 不同产品的运行情况不同，需要分开了解。首页展示各产品的在线率、设备数，让管理者掌握各产品的整体运行状态。

### 设备指令执行弹框
**背景：** 在移动端下发控制指令时，操作员需要确认操作。自定义弹框展示指令名称和参数，操作员确认后执行，执行后显示成功/失败反馈。替代系统原生弹框，样式统一、体验更好。

### App 用户认证
**背景：** 移动端需要安全的登录认证机制。平台使用自定义 Token 认证，登录后携带 Token 访问接口，支持 Token 刷新和自动续期。

## 北向接入

### 开放平台
**背景：** 第三方系统需要获取平台数据（ERP 系统取产量数据、MES 系统取设备状态）。开放平台提供标准 RESTful API，通过 AppId/AppSecret + OAuth2 认证，第三方系统安全地获取设备数据。

### Kafka 数据转发
**背景：** 企业已有大数据平台或数据中台，需要设备数据实时流入。平台将设备数据实时转发到 Kafka 消息队列，下游系统订阅消费。

### MQTT Broker 数据转发
**背景：** 设备数据需要转发到其他 MQTT 系统（如第三方云平台、总部监控系统）。平台作为 MQTT 客户端将设备数据转发到目标 Broker。

### HTTP 接口转发
**背景：** 一些系统通过 HTTP 接口接收数据（如企业自建平台、政府监管平台）。平台将设备数据通过 HTTP POST 推送到目标接口。

### 演示环境
**背景：** 潜在客户在采购前需要体验平台功能和操作流程。在线演示环境免安装免配置，直接登录体验，降低评估成本。

## 用户管理

### 第三方社交用户绑定
**背景：** 移动端用户习惯使用微信、支付宝等社交账号登录，不需要单独注册账号。平台支持微信小程序/公众号、支付宝等多种第三方平台登录绑定。

### 系统用户管理
**背景：** 平台需要管理多个用户账号，分配不同的访问权限。系统用户管理支持新增、编辑、禁用用户，统一管理用户信息。

### 菜单/权限管理
**背景：** 不同角色的用户应该看到不同的页面和功能。菜单和权限管理控制用户能访问哪些页面、能执行哪些操作，实现基于角色的访问控制。
